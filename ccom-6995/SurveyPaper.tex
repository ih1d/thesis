\caption{Conceptual architecture of Blue.
A Blue program is parsed into a tagless-final algebra with two
interpretations: a procedural interpretation \texttt{ProcRepr}
realizing $\llbracket\cdot\rrbracket_P$, and a translation interpretation
\texttt{GraphRepr} realizing $T$, which builds a graph that serves as the
runtime store. The graph is evaluated via $\llbracket\cdot\rrbracket_G$.
A Blue source program may also include \texttt{declareClause} statements
which install new translation clauses; each clause is checked for adequacy
against $\llbracket\cdot\rrbracket_P$ on admission and, if accepted,
extends $T$ for subsequent translation. The \texttt{:compare} command
in the REPL evaluates a program under both interpretations and reports
whether they agree, giving the user a runtime witness of the adequacy
property the system maintains.}
\label{fig:architecture}

\end{figure}

\section{What kind of evaluation would it need?}
Conceptual evaluation: the algebra-coverage property is typechecked; the adequacy check catches a sample of disagreements on test inputs; the worked example (loops + mutable state) demonstrates the system handles a construct outside the base translation.
Comparative evaluation: against TorchDynamo (translation is sound by check, not opportunistic), against TensorRight (translation extension rather than graph rewrite), against MLIR (reflective rather than statically declared extensions).
Future evaluation: once mechanized, the adequacy theorem replaces sampling with a proof. Stating this as future evaluation is honest and shows you understand the trajectory.
